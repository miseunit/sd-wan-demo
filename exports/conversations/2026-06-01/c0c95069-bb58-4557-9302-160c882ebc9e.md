## 🎯 产品分析

### 当前问题

你现在有 **两套完全独立的链路模型**：

| 模型 | 表名 | 所属 | 特点 |
|------|------|------|------|
| `SiteLink` | `site_links` | 站点管理 | 字段少，直接挂在站点下 |
| `WanLink` | `wan_links` | 链路管理 | 字段丰富（SLA评分、切换策略、月成本等） |

两者之间 **没有任何关联**，各管各的。站点管理只能在自己那套简陋的 `SiteLink` 里切换，链路管理那边建了丰富的链路数据，站点这边完全看不到。

---

### 你的思路方向是对的，但可以更自然

你说的「在站点里选现有链路作为备用链路」本质是 **把两套模型打通**。这个直觉完全正确。

但从 SD-WAN 的真实业务来看，我建议换个更简洁的思路：

### ✅ 推荐方案：让 WanLink 成为链路的唯一数据源

**核心改动：`SiteLink` 不再自己存链路信息，改为引用 `WanLink`。**

```
Before (割裂的):
  Site → SiteLink (自己存 link_type, isp, ip, bandwidth...)
  WanLink (独立存在，跟站点管理没关系)

After (打通的):
  Site → SiteLink (只存 wan_link_id + status)
                ↘ 引用 WanLink (链路的完整信息都在这里)
```

---

### 📐 交互流程设计

#### 场景一：站点管理 → 查看链路

1. 点击某个站点 → 打开详情 Drawer
2. 「链路」Tab 展示该站点下所有关联的链路（从 `SiteLink` 关联查 `WanLink`）
3. 每条链路显示完整信息：类型、ISP、SLA评分、健康状态、利用率等（数据来自 `WanLink`）

#### 场景二：站点管理 → 新增备用链路（你说的核心功能）

1. 在站点详情的链路 Tab 里，点击 **「+ 绑定链路」** 按钮
2. 弹出 Modal，显示一个下拉/表格，列出 **可用的 WanLink**（排除已绑定的）
3. 用户勾选一条或多条 → 确认绑定
4. 绑定后该链路状态默认为 `standby`（备用）

> 这就是你说的「下拉勾选」，完全符合你的想法。

#### 场景三：站点管理 → 切换活跃链路

1. 在链路列表中，点击某条备用链路的 **「切换为主链路」** 按钮
2. 触发切换逻辑，更新 `Site.active_link_id` + `SiteLink.status`
3. 与链路管理那边的数据保持联动（因为引用的是同一条 `WanLink`）

#### 场景四：链路管理 → 创建链路

1. 链路管理里正常创建 `WanLink`（选择所属站点、填写ISP/带宽/策略等）
2. 创建后，如果该站点想在站点管理里使用这条链路，需要在站点那边 **手动绑定**
3. 或者可以加一个选项：「创建后自动绑定为备用链路」→ 自动创建 `SiteLink` 关联记录

---

### 🧠 为什么这么设计

| 决策 | 理由 |
|------|------|
| WanLink 作为唯一数据源 | 一条链路只有一个真相，避免 `SiteLink` 和 `WanLink` 数据不一致 |
| SiteLink 变为关联表 | SD-WAN 里链路是独立资源，可以被不同站点引用（比如共享 Internet 出口） |
| 站点手动绑定 | 给管理员控制权，不是所有链路都要挂到站点上 |
| 支持多选绑定 | 一个站点可以有主链路 + 多条备用链路，符合 SD-WAN 冗余设计 |
| 绑定后可在两边看到 | 站点管理能看到该站点的链路，链路管理能看到链路被哪些站点使用 |

---

### 📊 数据模型改动示意

```
SiteLink 表改造:
  id            → 保留（主键）
  site_id       → 保留（站点FK）
  wan_link_id   → 新增（指向 WanLink.id，替代原来重复的那些字段）
  status        → 保留（active/standby）
  priority      → 新增（优先级排序，决定切换顺序）
  
  删除: link_type, isp, ip, bandwidth, used_bandwidth, 
        usage_percent, latency, loss（这些从 WanLink 读取）
```
