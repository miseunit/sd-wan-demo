## 智能选路与流量策略 — 完善需求文档

### 一、功能定位

本功能是对现有**策略管理**（通用 CRUD）和**链路管理**（性能监控）的**上层封装**，提供面向 SD-WAN 场景的结构化选路配置和可视化路径推荐。

> 现有策略管理中的 `route`（路由策略）、`qos`（QoS 策略）、`app_aware`（应用感知策略）类型已经预留了扩展点，本功能将这些类型从"JSON 自由编辑"升级为"结构化表单 + 可视化"。

interface RoutingMatchConditions {
    source_sites: string[];       // 源站点 ID 列表（复用现有 Site.id）

        end: string;              // "18:00"
        weekdays: number[];       // [1,2,3,4,5] = 周一到周五
    };
}

// 选路策略 — action_config 结构
interface RoutingActionConfig {
    routing_mode: 'primary-backup' | 'load-balance' | 'smart';
    // 主备模式
    primary_link_id?: string;     // 主链路 ID（复用现有 WanLink.id）
    backup_link_ids?: string[];   // 备用链路 ID 列表

        weight: number;           // 权重 1-100
    }[];
    // 智能选路依据
    smart_criteria?: {
        metrics: ('latency' | 'loss' | 'bandwidth')[];  // 选路依据指标
        latency_threshold?: number;   // ms，低于此值认为合格
        loss_threshold?: number;      // %，低于此值认为合格
        bandwidth_threshold?: number; // %，利用率低于此值认为合格
    };
    // 链路优先级排序（所有模式通用）

## 核心问题：这个设计是"功能导向"而不是"场景导向"

### 1. Tab 拆分反人类

实际运维中，我脑子里想的是：

> "上海分支的 VoIP 最近质量不行，我要看看它现在走的哪条路，能不能切到更好的链路"

按现在的 Tab 拆分，我得：
- 先去 Tab2 找 VoIP 应用策略 → 看它绑了哪个选路策略
- 再去 Tab1 找那个选路策略 → 看它配了哪些链路
- 最后去 Tab3 选源/目的/应用 → 看推荐路径

**跳了三个 Tab 才完成一个操作**，太割裂了。

### 2. Tab1 选路策略配置太"抽象"

在真实 SD-WAN 平台（Viptela、Fortinet、华为云网）里，选路策略不是孤立配置的，它是**绑在站点上**的。我更习惯的思路是：

> "这个站点有 3 条链路，我要决定流量怎么分配"

而不是先去一个全局策略池里建策略，再回来关联站点。

### 3. Tab3 智能选路才是核心，但它排最后

日常 80% 的时间花在**看路径 + 排障**，只有 20% 在配策略。现在的设计把"看"放在了最不重要的位置。

### 4. 应用识别不该让用户手动配 DPI

真正的 SD-WAN 设备（Aruba EdgeConnect、Cisco Viptela）DPI 是内置的，用户只管选"这个流量是 VoIP"，不用自己写 DPI 规则和端口号。把识别规则暴露给用户，反而增加使用门槛。

**这个视图的核心设计思路：**

1. **上来就是选站点对**，不是选策略。因为我的思维是"A 到 B 的流量怎么走"，不是"我要配个策略"
2. **推荐路径 + 链路实况 + 当前策略在一个页面里**，不用跳转
3. **快捷操作直接在结果旁边**——看到推荐路径不满意，一键切换；看到链路质量不行，直接编辑策略
4. **链路质量是实时的**，不是配置时填的静态值（复用现有 `getLinks()` 接口的 latency/loss/bandwidth）

## 总结

| 原方案 | 改进后 |
|--------|--------|
| 3 个 Tab 平级 | 2 个视图：路径总览（主）+ 策略配置（辅） |
| 先配策略，再看效果 | 先看路径和链路质量，再调整策略 |

| DPI 规则手动配置 | 应用类型预置下拉，高级用户才展开自定义 |

第一个方案本质上是"把配置表单分类摆好"，它适合**产品的第一个版本用来凑功能**，但不适合真正用起来。原因很简单——

SD-WAN 的日常操作是这样的：

> 早上到公司 → 打开平台 → 看一眼各站点链路质量 → 发现某个分支 VoIP 质量不行 → 点进去看它走的哪条路 → 换一条试试

这个流程里，**"看"和"改"是在同一个上下文里完成的**。3 个 Tab 的设计把看和改拆开了，每次切换 Tab 都要重新建立心理模型，用着累。

## 做了什么

### 后端（1 个新文件）

**[smart_routing.py](backend/app/api/endpoints/smart_routing.py)** — 3 个接口：

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/v1/smart-routing/app-types` | GET | 返回预置应用类型列表（VoIP/视频会议/Web等） |
| `/api/v1/smart-routing/recommend` | GET | 根据源站点+目的站点+应用类型，返回 Top3 推荐路径 |
| `/api/v1/smart-routing/source-links` | GET | 获取指定站点的所有链路实况数据 |

路径推荐算法：
- 同类型链路直连匹配（MPLS↔MPLS, Internet↔Internet, 5G↔5G）
- 通过 overlay 隧道中转匹配
- 综合打分：SLA 40% + 延迟 30% + 丢包 20% + 带宽 10%
- 根据应用类型自动调整阈值（VoIP 要求延迟 <50ms，Web 允许 200ms）
